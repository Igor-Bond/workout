# Развёртывание

Два независимых дела: **где лежит приложение** (GitHub Pages) и **где лежат
данные** (Firestore). Второе необязательно — без него приложение работает
полностью, просто не переносит данные между устройствами.

---

## 1. Синхронизация: проект Firebase

### 1.1. Создать проект

1. Открыть [console.firebase.google.com](https://console.firebase.google.com),
   нажать «Добавить проект».
2. Имя любое, например `workout-tracker`.
3. Google Analytics можно отключить — приложению он не нужен.

### 1.2. Включить вход через Google

1. В проекте: **Build → Authentication → Get started**.
2. Вкладка **Sign-in method** → **Google** → включить.
3. Указать почту поддержки (своя же) и сохранить.
4. Вкладка **Settings → Authorized domains**: добавить домен, откуда
   приложение открывается. Для GitHub Pages это `<логин>.github.io`.
   `localhost` уже в списке.

Без последнего шага вход будет молча закрываться с ошибкой
`auth/unauthorized-domain`.

### 1.3. Создать базу

1. **Build → Firestore Database → Create database**.
2. Регион — ближайший (`eur3` для Европы).
3. Режим — **production**: правила всё равно заменяются на следующем шаге.

### 1.4. Загрузить правила доступа

Открыть **Firestore Database → Rules**, вставить содержимое
[`firestore.rules`](firestore.rules) и нажать **Publish**.

Это обязательный шаг, а не рекомендация. Идентификатор проекта и ключ
приложения не секретны — Google по замыслу встраивает их в клиентский код,
и любой посетитель сайта их видит. Данные защищают только эти правила.

### 1.5. Прописать конфигурацию

1. **Project settings → General → Your apps → Web (`</>`)**.
2. Зарегистрировать приложение, имя любое, Firebase Hosting **не** включать.
3. Скопировать объект `firebaseConfig` и перенести значения в
   [`js/firebase.config.js`](../js/firebase.config.js).

```js
export const firebaseConfig = {
    apiKey: 'AIza...',
    authDomain: 'workout-tracker.firebaseapp.com',
    projectId: 'workout-tracker',
    storageBucket: 'workout-tracker.appspot.com',
    messagingSenderId: '000000000000',
    appId: '1:000000000000:web:abcdef'
};
```

### 1.6. Проверить

1. Открыть приложение, «Профиль → Синхронизация → Войти через Google».
2. После входа нажать «Синхронизировать».
3. В консоли Firebase: **Firestore Database → Data** — должна появиться
   коллекция `users/<ваш uid>` с подколлекциями `exercises`, `workouts`,
   `templates`, `bodyWeight`.

Что должно быть видно:

- тренировка **со статусом `active` в облако не уезжает** — так задумано
  (§39 ТЗ). Синхронизируются только завершённые;
- подходы лежат **внутри документа тренировки**, отдельной коллекции у них
  нет — так первая синхронизация на новом устройстве читает двести
  документов вместо пяти тысяч.

### 1.7. Расход бесплатного тарифа

Бесплатный тариф Spark даёт 50 000 чтений и 20 000 записей в сутки. Год
занятий — около двухсот тренировок, то есть двести документов. Обмен идёт
только изменившимся, по метке `updatedAt`, поэтому обычная синхронизация
читает единицы документов. Упереться в лимит одним пользователем
практически невозможно.

## 2. Публикация на GitHub Pages

1. Создать репозиторий и запушить содержимое проекта.
2. **Settings → Pages → Source: Deploy from a branch**, ветка `main`,
   папка `/ (root)`.
3. Через минуту приложение доступно по адресу
   `https://<логин>.github.io/<репозиторий>/`.
4. Добавить этот домен в Authorized domains (шаг 1.2), иначе вход не
   заработает.

Что важно не сломать:

- файл `.nojekyll` в корне обязателен;
- все пути в проекте относительные — приложение работает и из подкаталога;
- `manifest.json` ждёт `./index.html`, имя основного файла менять нельзя;
- при изменении состава файлов поднимать `APP_VERSION` в `sw.js`, иначе у
  установленных приложений останется старый кэш.

### Почему подкаталог — отдельная забота

На GitHub Pages приложение живёт не в корне домена, а по адресу
`/<репозиторий>/`. Любой путь, начинающийся со слэша, там указывает мимо.

Проверить локально: положить проект в подкаталог и поднять сервер над
родительской папкой.

```bash
powershell -ExecutionPolicy Bypass -File tools/serve.ps1 -Port 4180 -Root ..
```

Затем открыть `http://localhost:4180/workout/`. Сервер отдаёт `index.html`
для каталога так же, как это делает GitHub Pages.

Отдельно стоит помнить про `sw.js`: он регистрируется относительным путём,
поэтому его область действия — тот самый подкаталог, а все адреса в
`PRECACHE_URLS` считаются от него же. Проверки вида
`pathname.includes('/js/')` внутри воркера от префикса не страдают.

## 2.1. Проверить перед выкладкой

- [ ] `tests/index.html` — все проверки зелёные;
- [ ] `powershell -ExecutionPolicy Bypass -File tools/check-precache.ps1` —
      список офлайн-файлов сходится с деревом проекта;
- [ ] в консоли браузера пусто на всех разделах;
- [ ] приложение открывается из подкаталога (см. выше);
- [ ] `APP_VERSION` в `sw.js` поднят;
- [ ] `VERSION` в `js/version.js` поднят и виден в профиле;
- [ ] в `js/firebase.config.js` нет чужих ключей, если проект публичный;
- [ ] `docs/STATUS.md` отражает то, что есть на самом деле;
- [ ] офлайн: отключить сеть, перезагрузить — приложение открывается,
      история и статистика на месте.

### Установка на телефон

Android: открыть адрес в Chrome → появится предложение установить, либо
меню → «Установить приложение».

iPhone: Safari → «Поделиться» → «На экран Домой». Метки строки состояния
iOS запоминает в момент добавления значка; если они менялись, значок нужно
удалить и добавить заново.

## 2.2. Откат к стабильной версии

Перед крупной переработкой на работающее состояние ставится метка:

```
git tag -a v2.24.1 -m "Стабильная версия 2.24.1"
git push origin v2.24.1
```

`git tag -n5` показывает список меток с описанием — что именно в каждой
проверено.

### Если новое сломало работающее

Ветка `main` — это то, что выложено на Pages, поэтому откат делается
обычным коммитом поверх, а не переписыванием истории. Переписывание сломало
бы копии на других устройствах и не даёт понять задним числом, что
случилось.

```
git revert --no-commit v2.24.1..HEAD
git commit -m "Откат к v2.24.1: <что именно сломалось>"
git push origin main
```

**После отката обязательно поднять `APP_VERSION` в `sw.js`.** Иначе у тех,
кто уже получил сломанную версию, воркер останется прежним и продолжит
отдавать её из кэша: файлы в репозитории откатились, а на телефоне ничего
не изменилось.

Номер `VERSION` в `js/version.js` при откате не понижается, а растёт:
версия — это отметка «что сейчас стоит», а не «какой код внутри». Понижение
означало бы, что приложение помолодело, и проверка обновления перестала бы
считать новое новым.

### Данные откат не трогает

История лежит в браузере и в облаке, а не в коде: возврат к прежней версии
приложения её не отменяет. Опасность одна — миграции схемы базы (§34): они
поднимают номер версии базы, и старый код к новой схеме уже не откроется.
Поэтому перед переработкой, которая трогает схему, стоит выгрузить копию
через профиль — она читается любой версией.

## 3. Перенос истории из прошлой версии

История версии 1 лежит в `localStorage` браузера под ключом
`workout_history_v2`. Это хранилище привязано к источнику и профилю
браузера, поэтому данные из другого браузера или другого профиля само
приложение увидеть не может.

Порядок:

1. Открыть [`tools/export-v1.html`](../tools/export-v1.html) — там готовая
   строка для консоли и объяснение, где её выполнять.
2. Выполнить её в том браузере, где работала версия 1: `F12` → Console →
   вставить → Enter. Сохранится файл `workout-v1-<дата>.json`.
3. Перенести файл на нужное устройство.
4. В приложении: «Профиль → Резервная копия → Загрузить из файла».

Приложение узнаёт формат само, склеивает упражнения по названию с уже
существующими и не добавляет тренировки, которые уже загружены — повторный
выбор того же файла ничего не испортит.

## 4. Резервная копия

Независимо от облака: «Профиль → Резервная копия → Выгрузить в файл».
Обычный JSON — тренировки, упражнения, шаблоны и вес тела. Настройки в
копию не входят: часть из них привязана к устройству.

Загрузка предлагает два режима: **объединить** (побеждает более свежая
запись, то же правило, что и в облаке) и **заменить всё**.

Настройки в копию входят, но только переносимые: длительность отдыха,
режим выполнения, звук и вибрация. Привязанное к устройству — включено ли
здесь облако, когда здесь был обмен — не переносится: иначе новое
устройство получило бы неверные сведения о самом себе.
